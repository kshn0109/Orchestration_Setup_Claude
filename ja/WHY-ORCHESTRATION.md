# オーケストレーション方式の導入効果 — 指揮・実行分離構造の分析

> 本書は同一フォルダのオーケストレーションセットアップ(SETUP.md,
> instructions.md, agents/, hooks/)の導入効果を記述する。導入手順は
> SETUP.md を参照。

## 要約

### 概要

本セットアップは、Claude Code のメインエージェント(最上位単価モデル)を
指揮役に限定し、コード作成・テスト・照会等の実行作業を難易度別の下位
エージェントに委任する構造である。深い設計は Opus 5(effort: high)、
一般実装は Opus 5(effort: medium)、単純作業は Haiku(effort: low)が
担当する。運用指針(勧告)と PreToolUse フックゲート(強制)の二重構造で
動作する。

### 期待効果

1. **コスト削減** — 開発過程で消費されるトークンの大半は、ボイラープレート
   作成、テスト実行、ログ確認等、判断を要しない作業で発生する。単一
   エージェント方式ではこれら全体が最高単価で課金されるが、本セットアップは
   作業難易度に単価を対応させる。作業規模が大きいほど削減幅は増大する。
2. **長時間作業の品質維持** — 探索過程のファイル内容と試行錯誤の記録は
   下位エージェントのコンテキストで消滅し、メインセッションには結果報告
   のみが蓄積される。コンテキスト飽和に伴う計画の喪失が防止され、
   マルチステップ作業の後半品質が維持される。
3. **動作の一貫性確保** — 委任指針のみでは、長時間セッションにおいて
   メインエージェントが直接実装へ回帰する現象(drift)を防止できない。
   フックゲートが直接コード修正をツール呼び出しレベルで遮断するため、
   ルール遵守が構造的に保証される。標準の自動委任はセッションごとの判断に
   依存し結果が非決定的だが、本セットアップは固定ルールと強制機構により
   これを決定論化する。

### 導入判断基準

- **適する**: 多数ファイルにまたがる実装・リファクタリング・調査等、
  規模のある作業が多い環境。作業規模に比例して効果が増大する。
- **適さない**: 1〜2 ファイル単位の小規模修正が中心の環境では、委任
  オーバーヘッドにより効果がない。ただし有効状態でも小規模修正は直接
  処理される設計であり、常時有効化による支障はない。
- **導入コスト**: インストール所要約 10 分、管理者権限不要。
  `fable on/off` で即時切り替え可能であり、完全撤去に対応する。

以下の各節は上記結論の根拠を記述する。

## 1. 単一エージェント方式との比較

通常の使用では、単一モデルが単一コンテキスト内で計画・探索・実装・テストを
すべて実行する。小規模作業ではこの方式が最速だが、作業規模が大きくなると
以下の問題が発生する。

### 1.1 コスト構造

最上位モデル(Fable)はトークン単価が最も高い。一方、実際の開発時間の大半は
ボイラープレート作成、テスト実行、ログ確認、検索等、判断を要しない作業が
占める。単一エージェント方式ではこれら全体が最高単価で課金される。

本セットアップの単価対応は以下のとおり。

| 作業の性格 | 担当 | モデル / effort |
| --- | --- | --- |
| 計画・分配・統合・最終判断 | メインセッション | Fable |
| 深い設計・根本原因分析 | deep-reasoner | Opus 5 / high |
| 一般の実装・修正・テスト・レビュー | executor | Opus 5 / medium |
| ビルド・照会・ログ・検索 | runner | Haiku / low |

例として、大量のビルドログ確認は runner(Haiku)が実行して要約のみを報告
するため、メインセッションの最高単価トークン消費は要約分に限定される。

### 1.2 コンテキストの保全

単一エージェント方式の主要なボトルネックはコストよりもコンテキストにある。
探索過程で読んだ多数のファイル、試行錯誤の diff、テスト出力の全文が単一
コンテキストに蓄積される。コンテキストが飽和すると要約(compaction)が
発生し、当初に策定した計画と制約が失われ、後半の作業品質が低下する。

オーケストレーション構造では、サブエージェントが独立した新規コンテキストで
作業し、メインセッションには最終報告のみが返却される。探索記録と試行錯誤は
サブエージェントの終了とともに破棄される。メインセッションには指示内容と
結果という高密度の情報のみが残存するため、長時間のマルチステップ作業でも
指揮側が全体計画を維持する。大規模作業ではこの効果がコスト削減効果を上回る。

### 1.3 思考強度の分離

effort フィールドにより思考強度が作業別に分離される。deep-reasoner は
high で難問を処理し、executor は medium で実装し、runner は low で即時
応答する。単一エージェントは軽微な修正とアーキテクチャ決定を同一強度で
処理するため、いずれに合わせても非効率が発生する。

### 1.4 制約事項

- **小規模作業でのオーバーヘッド**: サブエージェントの起動と指示作成に
  コストが発生する。このため指針は 1〜2 ファイルの小規模修正を直接処理の
  対象と規定し、ゲートもターンあたり 2 ファイルまで直接修正を許可する。
- **指示品質への依存**: サブエージェントはメインセッションの会話文脈を
  参照できない。目標・制約・完了条件を最初の指示に一括して含める必要が
  あり、分割して伝達すると再質問または範囲逸脱が発生する。指針がこれを
  ルールとして明記している。

## 2. 標準の自動委任・並列化との比較

Claude Code は標準状態でもサブエージェントの起動と並列化を自律的に実行
する。本セットアップが追加で提供するのは以下の三点である。

### 2.1 ルーティングのルール化

自動委任はモデルのセッションごとの判断に依存する。同一作業がセッションに
よって委任される場合とメインセッションで直接処理される場合があり、起動
されるサブエージェントのモデルも一定しない。本セットアップはルーティング
規則(推論→deep-reasoner、実装→executor、雑務→runner)を指針として固定し、
各作業が処理される単価と強度を予測可能にする。

### 2.2 モデルの決定論的固定

標準のサブエージェントはエイリアスベースであるため、クライアントの
バージョン変更時に同一定義が別モデルを参照しうる(例: `opus` エイリアスは
v2.1.219 以降 Opus 5 に解釈変更)。本セットアップは frontmatter に完全な
モデル ID(`claude-opus-5`, `claude-haiku-4-5-20251001`)を明記し、
バージョン変更およびエイリアス再解釈の影響を受けない。runner は
`tools: Bash, Read, Grep, Glob` でツールを制限し、雑務担当がコードを修正
する経路を遮断する。

### 2.3 強制ゲート

本セットアップの中核的な差別化要素である。委任指針は違反しても制裁がなく、
長時間セッションではモデルが指針を無視して直接実装へ回帰する現象が発生
する。PreToolUse フックゲートはメインエージェントの直接コード修正を
ターンあたり 2 ファイルに制限し、超過時はツール呼び出しを遮断して
(終了コード 2)、ブロックメッセージで委任を指示する。シェル経由の迂回
(sed -i, Set-Content, リダイレクト)も遮断対象である。サブエージェントの
呼び出しはすべて通過するため、委任経路は維持される。

すなわち自動委任が勧告水準に留まるのに対し、本セットアップは指針(勧告)の
上にゲート(強制)を重畳し、ルール遵守を構造的に保証する。

### 2.4 並列化の観点

並列実行自体は両方式とも可能である。差異は並列処理の単価と統制にある。
自動並列化は起動モデルと個数に対する統制がないが、本セットアップは独立
作業 N 件を executor N 個(中間単価)または runner N 個(最低単価)に
明示的に分配する。同時に指針は濫用を制限する — 単一作業は単一エージェント
で処理し、並列は独立作業に限り単一メッセージで一括起動する。検証・再確認
目的のエージェント生成を禁止し、不要なトークン消費を防止する。

## 3. 適用基準

| 状況 | 判断 |
| --- | --- |
| 多数ファイルにまたがる機能実装・リファクタリング・大規模修正 | 有効。コンテキスト保全とコスト効果が最大 |
| 独立作業が多数(例: モジュール別テスト追加) | 有効。明示的な並列分配に適合 |
| 長時間の探索・調査作業(ログ分析、コードベース把握) | 有効。探索記録がメインコンテキストに蓄積されない |
| タイポ・設定・ドキュメント修正等の小規模変更 | 有効状態の維持で可。ゲートが 2 ファイルまで直接修正を許可 |
| ユーザーが直接多数のファイルを修正する作業 | `fable off` で作業し、終了後に再有効化 |

## 4. 結論

1. **コスト** — 判断は最高単価、実行は中間単価、雑務は最低単価で処理される。
2. **コンテキスト寿命** — メインセッションには報告のみが蓄積され、長時間作業でも計画が維持される。
3. **予測可能性** — ルーティング規則とモデル ID 固定により、結果がセッション・バージョンに左右されない。
4. **一貫性の強制** — ゲートが drift をツール呼び出しレベルで遮断する。指針単独では達成できない部分である。
5. **統制された並列化** — 独立作業に限り適正単価で一括分配し、濫用防止ルールを含む。

コスト項目のみを考慮すれば低単価モデルの単独使用で代替可能に見えるが、実際の
効果の相当部分はコンテキスト分離(2)と一貫性の強制(4)から生じる。低単価
モデルの単独使用は判断品質が低下し、高単価モデルの単独使用はコンテキストと
コストが先に限界へ達する。指揮と実行の分離は両者を同時に確保する構造である。
