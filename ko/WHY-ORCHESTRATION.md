# 오케스트레이션 방식 도입 효과 — 지휘·실행 분리 구조 분석

> 본 문서는 동일 폴더의 오케스트레이션 셋업(SETUP.md, instructions.md,
> agents/, hooks/)의 도입 효과를 기술한다. 설치 절차는 SETUP.md를 참조.

## 요약

### 개요

본 셋업은 Claude Code의 메인 에이전트(최상위 단가 모델)를 지휘 역할로
한정하고, 코드 작성·테스트·조회 등의 실행 작업을 난이도별 하위
에이전트에 위임하는 구조이다. 심층 설계는 Opus 5(effort: high), 일반
구현은 Opus 5(effort: medium), 단순 잡무는 Haiku(effort: low)가 담당한다.
운영 지침(권고)과 PreToolUse 훅 게이트(강제)의 이중 구조로 동작한다.

### 기대 효과

1. **비용 절감** — 개발 과정에서 소비되는 토큰의 대부분은 보일러플레이트
   작성, 테스트 실행, 로그 확인 등 판단이 불필요한 작업에서 발생한다.
   단일 에이전트 방식은 해당 작업 전체가 최고 단가로 과금되나, 본 셋업은
   작업 난이도에 단가를 대응시킨다. 작업 규모가 클수록 절감 폭이 커진다.
2. **장시간 작업의 품질 유지** — 탐색 과정의 파일 내용과 시행착오 기록은
   하위 에이전트의 컨텍스트에서 소멸하고, 메인 세션에는 결과 보고만
   축적된다. 컨텍스트 포화에 따른 계획 유실이 방지되어 멀티스텝 작업의
   후반 품질이 유지된다.
3. **동작의 일관성 확보** — 위임 지침만으로는 장시간 세션에서 메인
   에이전트가 직접 구현으로 회귀하는 현상(drift)을 방지할 수 없다. 훅
   게이트가 직접 코드 수정을 도구 호출 수준에서 차단하므로 규칙 준수가
   구조적으로 보장된다. 기본 자동 위임은 세션별 판단에 의존하여 결과가
   비결정적이나, 본 셋업은 고정 규칙과 강제 장치로 이를 결정론화한다.

### 도입 판단 기준

- **적합**: 다수 파일에 걸친 구현·리팩터링·조사 등 규모 있는 작업이 많은
  환경. 작업 규모에 비례하여 효과가 증가한다.
- **부적합**: 1~2개 파일 단위의 소규모 수정이 중심인 환경에서는 위임
  오버헤드로 인해 효과가 없다. 단, 활성 상태에서도 소규모 수정은 직접
  처리되도록 설계되어 있어 상시 활성화에 따른 지장은 없다.
- **도입 비용**: 설치 소요 약 10분, 관리자 권한 불필요. `fable on/off`로
  즉시 전환 가능하며 완전 제거를 지원한다.

이하 각 절은 상기 결론의 근거를 기술한다.

## 1. 단일 에이전트 방식과의 비교

통상적인 사용에서는 단일 모델이 단일 컨텍스트 내에서 계획·탐색·구현·
테스트를 전부 수행한다. 소규모 작업에서는 이 방식이 가장 빠르나, 작업
규모가 커지면 다음 문제가 발생한다.

### 1.1 비용 구조

최상위 모델(Fable)은 토큰 단가가 가장 높다. 반면 실제 개발 시간의
대부분은 보일러플레이트 작성, 테스트 실행, 로그 확인, 검색 등 판단이
불필요한 작업이 차지한다. 단일 에이전트 방식에서는 이 전체가 최고 단가로
과금된다.

본 셋업의 단가 대응은 다음과 같다.

| 작업 성격 | 담당 | 모델 / effort |
| --- | --- | --- |
| 계획·분배·종합·최종 판단 | 메인 세션 | Fable |
| 심층 설계·근본원인 분석 | deep-reasoner | Opus 5 / high |
| 일반 구현·수정·테스트·리뷰 | executor | Opus 5 / medium |
| 빌드·조회·로그·검색 | runner | Haiku / low |

예를 들어 대량의 빌드 로그 확인은 runner(Haiku)가 수행하고 요약만
보고하므로, 메인 세션의 최고 단가 토큰 소비는 요약 분량으로 제한된다.

### 1.2 컨텍스트 보전

단일 에이전트 방식의 주요 병목은 비용보다 컨텍스트에 있다. 탐색 과정에서
읽은 다수의 파일, 시행착오의 diff, 테스트 출력 전문이 단일 컨텍스트에
누적된다. 컨텍스트가 포화되면 요약(compaction)이 발생하고, 초기에 수립한
계획과 제약이 손실되어 후반 작업의 품질이 저하된다.

오케스트레이션 구조에서는 서브에이전트가 독립된 신규 컨텍스트에서
작업하고, 메인 세션에는 최종 보고만 반환된다. 탐색 기록과 시행착오는
서브에이전트 종료와 함께 폐기된다. 메인 세션에는 지시 내용과 결과라는
고밀도 정보만 잔존하므로, 장시간 멀티스텝 작업에서도 지휘자가 전체 계획을
유지한다. 대규모 작업에서는 이 효과가 비용 절감 효과를 상회한다.

### 1.3 사고 강도의 분리

effort 필드에 의해 사고 강도가 작업별로 분리된다. deep-reasoner는 high로
난제를 처리하고, executor는 medium으로 구현하며, runner는 low로 즉시
응답한다. 단일 에이전트는 사소한 수정과 아키텍처 결정을 동일 강도로
처리하므로, 어느 쪽에 맞추어도 비효율이 발생한다.

### 1.4 제약 사항

- **소규모 작업에서의 오버헤드**: 서브에이전트 기동과 지시 작성에 비용이
  발생한다. 이에 따라 지침은 1~2개 파일의 소규모 수정을 직접 처리
  대상으로 규정하며, 게이트도 턴당 2개 파일까지 직접 수정을 허용한다.
- **지시 품질 의존성**: 서브에이전트는 메인 세션의 대화 맥락을 참조할 수
  없다. 목표·제약·완료 조건을 최초 지시에 일괄 포함해야 하며, 분할 전달
  시 재질의 또는 범위 이탈이 발생한다. 지침이 이를 규칙으로 명시한다.

## 2. 기본 자동 위임·병렬화와의 비교

Claude Code는 기본 상태에서도 서브에이전트 기동과 병렬화를 자율적으로
수행한다. 본 셋업이 추가로 제공하는 것은 다음 세 가지이다.

### 2.1 라우팅의 규칙화

자동 위임은 모델의 세션별 판단에 의존한다. 동일 작업이 세션에 따라
위임되기도 하고 메인 세션에서 직접 처리되기도 하며, 기동되는
서브에이전트의 모델도 일정하지 않다. 본 셋업은 라우팅 규칙
(추론→deep-reasoner, 구현→executor, 잡무→runner)을 지침으로 고정하여,
각 작업이 처리되는 단가와 강도를 예측 가능하게 한다.

### 2.2 모델의 결정론적 고정

기본 서브에이전트는 별칭 기반이므로 클라이언트 버전 변경 시 동일 정의가
다른 모델을 참조할 수 있다(예: `opus` 별칭은 v2.1.219부터 Opus 5로 해석
변경). 본 셋업은 frontmatter에 전체 모델 ID(`claude-opus-5`,
`claude-haiku-4-5-20251001`)를 명시하여 버전 변경과 별칭 재해석의 영향을
받지 않는다. runner는 `tools: Bash, Read, Grep, Glob`으로 도구를 제한하여
잡무 담당이 코드를 수정하는 경로를 원천 차단한다.

### 2.3 강제 게이트

본 셋업의 핵심 차별 요소이다. 위임 지침은 위반하여도 제재가 없으며,
장시간 세션에서 모델이 지침을 무시하고 직접 구현으로 회귀하는 현상이
발생한다. PreToolUse 훅 게이트는 메인 에이전트의 직접 코드 수정을 턴당
2개 파일로 제한하고 초과 시 도구 호출을 차단하며(종료 코드 2), 차단
메시지로 위임을 지시한다. 셸 경유 우회(sed -i, Set-Content, 리다이렉트)도
차단 대상이다. 서브에이전트의 호출은 전부 통과하므로 위임 경로는 유지된다.

즉 자동 위임이 권고 수준에 머무르는 반면, 본 셋업은 지침(권고) 위에
게이트(강제)를 중첩하여 규칙 준수를 구조적으로 보장한다.

### 2.4 병렬화 관점

병렬 실행 자체는 양쪽 모두 가능하다. 차이는 병렬 처리의 단가와 통제에
있다. 자동 병렬화는 기동 모델과 개수에 대한 통제가 없으나, 본 셋업은
독립 작업 N건을 executor N개(중간 단가) 또는 runner N개(최저 단가)로
명시적으로 분배한다. 동시에 지침은 남용을 제한한다 — 단일 작업은 단일
에이전트로 처리하고, 병렬은 독립 작업에 한하여 단일 메시지로 일괄
기동한다. 검증·재확인 목적의 에이전트 생성을 금지하여 불필요한 토큰
소비를 방지한다.

## 3. 적용 기준

| 상황 | 판단 |
| --- | --- |
| 다수 파일에 걸친 기능 구현·리팩터링·대규모 수정 | 활성. 컨텍스트 보전과 비용 효과가 최대 |
| 독립 작업 다수(예: 모듈별 테스트 추가) | 활성. 명시적 병렬 분배에 적합 |
| 장시간 탐색·조사 작업(로그 분석, 코드베이스 파악) | 활성. 탐색 기록이 메인 컨텍스트에 누적되지 않음 |
| 오타·설정·문서 수정 등 소규모 변경 | 활성 상태 유지 가능. 게이트가 2개 파일까지 직접 수정 허용 |
| 사용자가 직접 다수 파일을 수정하는 작업 | `fable off` 후 작업, 종료 후 재활성 |

## 4. 결론

1. **비용** — 판단은 최고 단가, 실행은 중간 단가, 잡무는 최저 단가로 처리된다.
2. **컨텍스트 수명** — 메인 세션에 보고만 축적되어 장시간 작업에서도 계획이 유지된다.
3. **예측 가능성** — 라우팅 규칙과 모델 ID 고정으로 결과가 세션·버전에 좌우되지 않는다.
4. **일관성 강제** — 게이트가 drift를 도구 호출 수준에서 차단한다. 지침 단독으로는 달성 불가한 부분이다.
5. **통제된 병렬화** — 독립 작업에 한하여 적정 단가로 일괄 분배하며, 남용 방지 규칙을 포함한다.

비용 항목만 고려하면 저단가 모델의 단독 사용으로 대체 가능해 보이나, 실제
효과의 상당 부분은 컨텍스트 분리(2)와 일관성 강제(4)에서 발생한다. 저단가
모델 단독 사용은 판단 품질이 저하되고, 고단가 모델 단독 사용은 컨텍스트와
비용이 먼저 한계에 도달한다. 지휘와 실행의 분리는 양자를 동시에 확보하는
구조이다.
